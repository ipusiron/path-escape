PathEscape — ディレクトリートラバーサル体験ツール

クライアントサイドで動く仮想ファイルシステムを使って `../` によるパス操作を学びます。

⚠️ 教育目的専用：このツールは学習専用です。実際のWebサイトへの攻撃は法的に禁止されています。

PathEscape の使い方

🎯 クイックスタート

  1. 攻撃体験タブを選択（デフォルト）
  2. パス入力欄に /app/files/readme.md を入力してFetch
  3. /robots.txt で機密パスのヒントを探す
  4. 次に ../../etc/passwd や ../../secrets/flag.txt を試す
  5. ヒントボタンで攻略のコツを確認

🔍 フィルターと、それを破る手法

フィルターごとに欠陥があり、破る手法が1つ対応します。目標はいつも /secrets/flag.txt を取ることです。

1. なし（フィルターなし）

  • そのまま上に戻れます。例: ../../secrets/flag.txt
  • まず /robots.txt で機密パスのヒントを探すのも手です

2. 生の「..」を弾く

  • 欠陥: デコードする前の入力しか見ないので、エンコードされた ..を見逃します
  • 破る手法（URLエンコード）: %2e%2e/%2e%2e/secrets/flag.txt

3. 「../」を消す

  • 欠陥: ../を消したあと、結果を見直しません
  • 破る手法（入れ子）: ....//....//secrets/flag.txt（内側を消すと ../../ が組み上がる）

4. デコードして「..」を弾く

  • 欠陥: 1回だけデコードして確認し、その後もう1回デコードされます
  • 破る手法（二重エンコード）: %252e%252e%252f%252e%252e%252fsecrets%252fflag.txt

5. 拡張子チェック（画像だけ）

  • 欠陥: 末尾の拡張子だけ見て許可し、取得は \0（ヌルバイト）で切ります
  • 破る手法（ヌルバイト）: ../../secrets/flag.txt%00.png（拡張子は .png で通り、取得は flag.txt）

🛡️ 防御の学習

  • Safe Modeに切り替えると、適切な対策が実装された状態を確認できます
  • 座学タブで詳しい技術解説と対策方法を学べます

💡 Tips

  • robots.txt活用: /robots.txt で機密ディレクトリーのヒントを発見
  • デバッグ: DevToolsのConsoleで Object.keys(window.VFS) を実行すると、仮想ファイルシステムの全パスが確認できます
  • ログ確認: 取得ログでリクエスト履歴とフィルター状況を確認
  • エラー分析: 出力ビューでファイル内容やエラーメッセージを確認
  • 手動クリア: ヒントは手動で×ボタンを押すまで表示され続けます

    対策結果
    パスを入力して Fetch を押すと、各対策の結果が出ます。

    ブラックリスト（../ を消す）は、入れ子や符号化で /app/files/ の外のファイルが漏れることがあります。正規化してから base を確かめる方法と、許可リストは、どの手法でも止めます。

    ディレクトリートラバーサル（Directory Traversal）は、パストラバーサル（Path Traversal）とも呼ばれ、Webアプリケーションがファイルパスを適切に検証しないことで、攻撃者が本来アクセスできないファイルやディレクトリーにアクセスできてしまう脆弱性です。

    基本的な仕組み

    多くのOSでは、..（ドットドット）は親ディレクトリーを表します。攻撃者はこの記号を悪用して、アプリケーションが意図したディレクトリーから外のファイルにアクセスします。

    正常なリクエスト: /app/files/readme.txt
攻撃的なリクエスト: /app/files/../../../etc/passwd

    なぜ危険なのか

    • 設定ファイル（データベース接続情報など）の漏洩
    • ソースコードの露出による別の脆弱性の発見
    • システムファイル（/etc/passwd、/etc/shadow）へのアクセス
    • 他ユーザーのデータへの不正アクセス

    1. 基本的な相対パス攻撃

    ../../../etc/passwd
..\..\..\..\windows\system32\config\sam

    最も単純な形式。..を繰り返して上位ディレクトリーに移動します。

    2. エンコーディング回避

    URLエンコード: %2e%2e%2f
ダブルURLエンコード: %252e%252e%252f
Unicodeエンコード: ..%c0%af

    フィルターを回避するために、さまざまなエンコーディングを使用します。

    3. Null文字インジェクション

    ../../../../etc/passwd%00.jpg

    一部の言語では%00（Null文字）以降を無視するため、拡張子チェックを回避できます。

    4. 絶対パス指定

    /etc/passwd
C:\windows\system32\config\sam

    相対パスではなく、絶対パスを直接指定する手法です。

    5. 入れ子（ダブルスラッシュ）

    ....//....//etc/passwd

    ../ を1回だけ文字列置換で消すフィルターを破ります。内側の ../ を消すと、外側の文字から ../ が組み上がります。スタック方式で正規化するフィルターには効きません（このツールの「../ を消す」フィルターで試せます）。

    CVE-2021-41773 — Apache HTTP Server 2.4.49

    2021年10月、2.4.49で入ったパスの正規化の不備。Aliasの外のファイルを読め、CGIが有効だとリモートコード実行につながりました。発見時点ですでに攻撃に使われていました。URLエンコードした .%2e/ で ../ を作る形が使われました。

    curl 'http://target/cgi-bin/.%2e/.%2e/.%2e/.%2e/etc/passwd'

    CVE-2021-42013 — 2.4.50の修正が不完全だった

    41773を直した2.4.50の修正が不十分で、数日後に別の形で再び破られました（2.4.49・2.4.50が対象、2.4.51で修正）。ランサムウェアの攻撃にも使われました。「1回ふさいでも、エンコードの入れ子で抜けられる」という、このツールのフィルターが見せる話そのものです。

    CVE-2020-5410 — Spring Cloud Config Server

    2020年、設定を配る Spring Cloud Config Server で、特別に細工したGETリクエストから任意のファイルを読めるディレクトリートラバーサル。CISAの「悪用が確認された脆弱性」に載りました。

    これらは、入力の検証とパスの正規化の大切さと、「修正が不完全だと再び破られる」ことを示しています。

    なぜこの脆弱性が生まれるのか

    開発者が「ユーザーは正しい入力をする」と仮定してしまうことが原因です。

    身近な例で理解する

    図書館で「3階の本を借りたい」と言われたとき、エレベーターのボタンを押してもらう場面を想像してください。

    • 正常：「3階」ボタンを押す
    • 攻撃：「地下2階（立入禁止の書庫）」ボタンを押す

    システムが「押されたボタンの階に行く」だけで、「行ってよい階かチェックしない」場合、問題が発生します。

    攻撃者の思考プロセス

    1. 偵察：エラーメッセージやURLパラメーターを観察
    2. 仮説：「ファイルパスを受け取っているようだ」
    3. 実験：../を追加してみる
    4. 確認：エラーメッセージが変わった？別のファイルが見えた？
    5. 拡大：より深いディレクトリーや重要なファイルを狙う

    よくある誤解

    • ❌「拡張子をチェックしているから安全」→ Null文字で回避可能
    • ❌「../を削除しているから安全」→ ....//で回避可能
    • ❌「WAFがあるから大丈夫」→ 新しい回避手法は常に発見される
    • ❌「内部システムだから関係ない」→ 内部犯行のリスクも存在

    1. 入力検証とサニタイゼーション

    // Node.js の例
const path = require('path');

function safeJoin(base, userInput) {
  const normalizedPath = path.normalize(path.join(base, userInput));
  if (!normalizedPath.startsWith(path.normalize(base))) {
    throw new Error('Invalid path');
  }
  return normalizedPath;
}

    const ALLOWED_FILES = ['readme.md', 'help.txt', 'manual.pdf'];
if (!ALLOWED_FILES.includes(requestedFile)) {
  return res.status(403).send('Access denied');

    3. chroot/コンテナーによる隔離

    FROM node:14-alpine
WORKDIR /app
COPY --chown=node:node . .
USER node

    4. 最小権限の原則

    • アプリケーションは必要最小限のファイルのみ読み取り可能に
    • 実行ユーザーの権限を制限
    • 機密ファイルは別のサーバー/ディレクトリーに配置

    5. セキュアコーディング実践

    # Python の例
import os

def get_file_safely(base_dir, file_name):
    safe_path = os.path.realpath(os.path.join(base_dir, file_name))
    if not safe_path.startswith(os.path.realpath(base_dir)):
        raise ValueError("Access denied")
    if not os.path.exists(safe_path):
        raise FileNotFoundError("File not found")
    return safe_path

    チェックリスト

    • ユーザー入力を信頼しない
    • パスを正規化してから検証
    • ベースディレクトリー外へのアクセスを防ぐ
    • 可能な限りホワイトリストを使用
    • エラーメッセージに詳細情報を含めない
    • ログを記録して異常なアクセスを検知
    • 定期的なセキュリティテストの実施

    関連する脆弱性

    • Local File Inclusion (LFI)：ローカルファイルを読み込んで実行
    • Remote File Inclusion (RFI)：外部ファイルを読み込んで実行
    • Path Manipulation：パス操作全般の脆弱性
    • Information Disclosure：情報漏洩の一種
